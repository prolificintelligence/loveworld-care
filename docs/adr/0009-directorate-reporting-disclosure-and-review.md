# ADR-0009: Directorate reporting authority, disclosure and accountable review

Date: 7 November 2026. Status: implemented; deployment evidence is recorded separately.

## Scope and suite ownership

This increment implements the institutional loop in LWH-ENG-002: obligations and returns (LWH-PRD-004), protected safety review (005), independent data stewardship (006), reviewed leadership evidence (007), and accountable interventions (008). It uses LWH-SPEC-003/004/007/008/009/010/011/014/016. The 78 controlled source documents, 200 requirements and 111 specified acceptance cases retain their original hashes and status. Native implementation contracts extend the suite without silently changing the archived definitions.

## Decisions

The existing cloud identity and stored grants remain authoritative. Directorate seniority does not create reporting, clinical or confidential safety-case access. Data Governor, Reporting Officer, Data Reviewer, Data Analyst, Executive Viewer, Programme Owner, Safety Reporter and Safety Reviewer are explicit, scoped, expiring roles. Global Data Governor adoption requires a global grant. Current authority is checked before an encrypted idempotency receipt can be replayed.

Obligations freeze an actual unit, its historical Region/Zone ancestry, reporting stream, UTC-aware period boundaries, IANA calendar timezone, deadline and exact adopted metric versions. Overlapping unit/stream periods are rejected. Facility activity, community activity and regional coordination are separate authorities. Nil, unknown, missing, partial and not applicable remain different values. A submitted return is not verified evidence. Verification requires another person and attributed source, method, scope and reasons for all warning overrides. Blocking arithmetic or contract findings cannot be overridden.

The controlled catalogue contains the 45 suite metric identifiers. It supplies authored definitions for review; it does not seed adopted policy. Count/decimal/ratio contracts, dimensions, populations, exclusions, permitted aggregation and source mappings require recorded adoption. Ratios use governed numerator/denominator aggregation. Distinct people are non-additive without reviewed reconciliation. The supported automatic EMR extractor reads actual completed encounters by disposition time, excludes entered-in-error sources and returns aggregate counts plus provenance hashes. It does not return patient identifiers, send charts to a model, or add manual and extracted feeds together.

Bulk CSV input is size/row bounded. Typed accepted, blocked and duplicate outcomes conserve every parsed source row; raw input is retained encrypted. A batch is a durable draft, not verified truth. CSV syntax or header failures reject the command safely. Formula-leading export fields are escaped, with identical disclosure rules for the API and export. See [OWASP CSV Injection](https://community.owasp.org/attacks/CSV_Injection) and [OWASP testing guidance](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/21-CSV_Injection/).

Cohorts freeze aligned expected unit-period obligations and an actually adopted disclosure policy. Independent release checks retained source versions again. Only verified returns contribute values; missingness, coverage and late receipt remain visible. Small cells, insufficient contributing units, withheld partial cohorts, related total/subtotal reconstruction, and overlapping or small-difference releases are suppressed. Policy thresholds and risk assessment are explicit adoption inputs. They are not a universal anonymity guarantee. Any later return change, including the first receipt for a previously missing obligation, invalidates existing cohort snapshots. Historical released values remain available with a stale designation; they are never rewritten as if the correction had always existed. Policy withdrawal or expiry blocks access and export.

Safety signals retain minimal private capture and a separate review history. Only the originator and assigned review purpose can inspect the case; originators do not receive private reviewer notes. An actual accepted, current duty window and active scoped reviewer are required for automatic assignment. Urgent signals without coverage remain unassigned with a named fallback escalation. Review acknowledgement, verified classification, unsubstantiated finding, duplicate linkage and closure are separate events. Contributing factors are observations, not certified cause. Adopted external receipt requirements block closure until recorded evidence exists. External receipts are attributed manual attestations, not a claim that an agency integration dispatched successfully. Offered review handovers preserve the current reviewer until the named, covered successor accepts.

Actions retain their evidence source version/state/hash, proposed owner, distinct fallback, independent reviewer, resources, dependencies and due/review dates. Assignment, acceptance, resource approval, progress, submitted evidence, reviewed completion and observed outcome remain distinct. Owner handovers require successor acceptance. Outcomes require limitations; completion does not prove causation. Daily authenticated job reconciliation and a manual Governor command record unique overdue exceptions. Only the named fallback can acknowledge an escalation; acknowledgement does not transfer case/action ownership or claim external notification. This daily job is not an emergency response scheduler.

Consequential reporting commands are serialised within PostgreSQL using a transaction advisory lock, expected versions and atomic encrypted receipts/history/outbox records. This keeps releases, corrections and duplicate submissions ordered across serverless instances. The tradeoff is a single reporting write lane; capacity must be qualified before higher-volume activation. [PostgreSQL locking documentation](https://www.postgresql.org/docs/current/explicit-locking.html) defines the transaction lock semantics. Immutable tables reject direct UPDATE/DELETE. Current records remain rebuildable/version-checked projections; signed clinical history remains under the existing EMR protections.

## Deployment, migration and rollback

Migration 3 is additive: reporting tables, immutable triggers and a new schema-version record. It preserves clinical data, existing encryption/authority keys, account credentials and provider configuration. The new API supports schema 2 while reporting waits for migration, and schema 3 after migration. Deploy that compatible API first, migrate, then deploy the frontend. No sample patients, returns, policies, safety cases or approvals are seeded.

A reporting-only rollback sets LWH_REPORTING_ENABLED=false and keeps the schema-3-compatible API, then restores the prior frontend if needed. Do not restore a schema-2-only API after migration 3, drop reporting tables, reverse accepted evidence or rotate the data key as a rollback mechanism. Any further database recovery requires its own reviewed operational procedure.

## Qualification and operating dependencies

Actual duty coverage, metrics/templates, calendar obligations, disclosure policy, safety categories and roles must be adopted by their authorised officers. None is fabricated at deployment. Private attachments still require the existing configured scanner before clearance; this increment stores evidence references/text rather than claiming scanned attachment availability. External agency dispatch, real-time alert delivery, broader EMR/LIS/PACS/FHIR feeds, narrative analysis, population incidence, open-ended BI slicing, large-scale throughput and recovery/restore qualification are not certified here. List views are bounded; obligation pagination and unit search are available, while complete searchable/paginated stewardship remains further work.

Engineering tests and isolated live PostgreSQL proofs establish the recorded software behaviour. Browser/accessibility testing, independent disclosure/security assessment, actual facility UAT and operational/clinical acceptance remain separate. Offline installation stays deferred at the project lead's request. No Playwright/browser software is installed.
