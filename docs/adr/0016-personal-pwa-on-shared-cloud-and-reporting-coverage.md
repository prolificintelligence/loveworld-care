# Personal PWA on the shared cloud and authoritative reporting coverage

Date: 9 November 2026. User decision: an installable My LW Health Care experience on the current deployment, connected to the existing platform API.

My LW Health Care has its own manifest, application name, PNG icons, standalone launch URL and scoped service worker. It remains part of `apps/platform-web` on the current Vercel origin. Staff, Directorate and patient experiences have separate routes and server permissions; this decision does not create a separate browser origin, separate patient database or isolated authentication system. Staff workspaces remain browser workspaces. Older demo applications elsewhere in the repository do not define current production capability.

The PWA launches `/my-health?source=installed`. The worker registration scope is `/my-health`; its navigation handler additionally matches only `/my-health` and `/my-health/…`. It ignores API, staff, cross-origin and non-GET requests. It stores no responses, records, credentials or drafts in Cache Storage and queues no background submissions. A failed navigation produces public connection guidance with HTTP 503/no-store. Live permission checks and care submissions require connectivity. This is separate from the deferred facility-local EMR/WAN-offline runtime.

Installation guidance uses the browser's actual install event when available and manual platform guidance otherwise. Installation completion is not invented from a button press. A manifest/worker/HTTP check is not an observed device-installation or accessibility acceptance test. Requirements and browser behaviour were checked against the [MDN installability guide](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable).

Personal requests remain asynchronous human care-team communication. They do not confirm a consultation, create a clinical encounter, initiate video, dispatch emergency services or prove receiving-facility referral acceptance. The existing EMR owns signed care, appointments and staff referral coordination. Patient-readable updates reach the verified recipient through reviewed releases or human request responses. A dedicated patient referral tracker and live teleconsultation remain separate work.

For the Director-first reporting priority, `/v1/reporting/coverage` calculates administrative totals in SQL across all permitted configured obligations, independent of UI page limits. It resolves current source-reporting/programme roles before aggregation. Overlapping grants do not duplicate obligations. Executive-only and platform-administrator-only roles cannot use this source operational route; released clinical intelligence remains behind the existing cohort/disclosure/review boundary.

Coverage counts unit-period obligations, not distinct facilities or clinical incidence. Current receipt means a submitted/verified current return with receipt metadata; drafts and returned corrections do not establish current submission. Empty denominators are null/not established. Optional period bounds must both be supplied, timezone-aware and ordered; filtering selects the exact frozen reporting period. All-period totals are labelled accordingly. No institutional definition, calendar, mandated template, expected-unit roster or disclosure policy is adopted by this code.

This is a schema-8 code/assets release. No new database tables, patient-data migration, external host or equipment connection is required. Qualification, actual deployment evidence and remaining operating acceptance are recorded separately in the release report.
