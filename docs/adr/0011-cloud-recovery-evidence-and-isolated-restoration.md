# ADR-0011: Operator-held recovery keys and isolated cloud restoration

Date: 8 November 2026. Contract: `LWH-EXT-CONTINUITY-001`. Scope: the existing Neon database and configured private object store. This implements the next cloud-compatible Phase 4A recovery/reconciliation increment under SPEC-015/016, ENG-005/006 and OPS-005. It does not amend the archived baseline or authorise clinical activation.

The online service holds the application encryption key and cannot itself demonstrate recovery after that key is lost. A separate recovery key therefore stays with the privileged operator tool; it is never provisioned to the Vercel web/API environments or exposed through an application route. `platform_continuity.py keygen` creates it once in an ignored operator directory with restrictive file permissions. Independent protected custody remains an actual operator duty; a local key file is not proof of off-site escrow.

An archive reads every known application table from one PostgreSQL REPEATABLE READ, READ ONLY transaction. A mismatch between the live table inventory and the application schema fails the archive. Rows are ordered by primary key, streamed in small fetches and split into size-bounded chunks. AES-GCM binds every chunk to its archive identity and logical path. The encrypted manifest carries counts, canonical hashes, schema/authority information and the application key required for recovery. Actual referenced private evidence bytes are checked against their immutable recorded size/hash and encrypted into the archive. A stored manifest appears only after all uploaded ciphertext has been read back and verified. Partial uploads never count as completed backups.

The archive deliberately contains no Vercel, email, AI or database-provider credentials. It restores logical application state, files and application key material. Provider account recovery, deployment configuration, secrets custody and independent copies retain their own procedures. Automated backup scheduling, cross-account/region protection and adopted RPO/RTO are not inferred from an operator-run archive.

A rehearsal always creates a fresh randomly named `lwh_restore_<32hex>` schema. There is no production restore target argument, destructive overwrite switch, public archive-download endpoint or automatic failover. Deferred constraints in the temporary schema allow self-referential hierarchy rows to load while still requiring actual referential integrity at transaction commit. The restored database is checked against the archived row counts/hashes; every encrypted field must decrypt using the archived application key. Clinical Ed25519 signatures, contiguous event chains, current-state/event agreement and reporting payload hashes are checked. The same immutable-history and signed-note protections are installed in the isolated schema.

Referenced files are actually recovered from encrypted objects into an isolated private prefix, read back and compared, then removed. The temporary database schema is also removed. Successful evidence is recorded only after cleanup completes; failed cleanup records an explicit exception. The rehearsal never starts an HTTP service, sends an email, processes a payment or adopts restored write authority. Resuming service after a real disaster requires fencing, preservation/reconciliation of newer care, configuration/secrets recovery and the relevant authorised service decisions.

Aggregate integrity observations check ledger groups, stock/movement reconciliation, missing/stale task indexes, active unowned alerts, expired leases and unresolved work. They are immutable observations rather than repairs or completion commands. Online observations have a time budget and each SQL statement sees its own committed snapshot; the UI does not describe them as a simultaneous full audit. The isolated recovery check runs over the restored transaction. A faithful restore with existing exceptions is separately labelled and never certifies service readiness.

Migration 5 adds one immutable assurance table. New recovery-evidence routes wait for schema 5; the existing controls/clinical/reporting runtime remains compatible with schema 4 during rollout. The platform-administrator UI receives counts, measured evidence, unresolved boundaries and audit references, never patient narratives, source identifiers, secret keys or archive payloads. Current authority is checked before cached command receipts. An operator CLI run is attributed to the service tool and does not impersonate a human reviewer.

Continuous workers, malware-scanner hosting, facility-local installation and full offline-care qualification remain deferred outside the current stack. Key rotation/versioned retirement, independent escrow/copies, adopted retention and recovery targets, representative-load recovery and witnessed operating acceptance remain separate work. No retention expiry, staffed contact, adoption or acceptance result is invented.

Primary database references: [repeatable-read and statement snapshots](https://www.postgresql.org/docs/current/transaction-iso.html) and [temporary-target constraint alteration](https://www.postgresql.org/docs/current/sql-altertable.html).
