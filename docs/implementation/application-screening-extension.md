# Application screening and pre-inspection evidence review

`LWH-EXT-APPLICATION-002` implements the initial application ordering in canonical SPEC-009 /STM-002 without changing the controlled baseline or adopting operating policy. It adds attributed metadata to existing immutable Application revisions; no table or migration is added.

The sequence is **DRAFT → SUBMITTED → SCREENING → EVIDENCE_REVIEW → INSPECTION → RECOMMENDED → DECIDED**. Assignment selects distinct, currently scoped reviewer and inspector and enters SCREENING. The assigned reviewer records an intentional, reasoned screening of the actual dossier; current retained criteria must match the facility type/jurisdiction and required submitted evidence must be current and scanned. This starts evidence review, not inspection or recognition.

The same personally assigned reviewer records an actual assessment and specific evidence IDs for every required criterion exactly once. Unknown/duplicated criteria, duplicated IDs, other-criterion/other-case, unscanned or expired evidence are refused. Optional criteria without evidence may be omitted; an empty assessment list is valid only when the retained adopted criteria require no evidence. No absence is silently converted to MET, a clinical zero or canonical tagged capture. A separate reason and explicit intent are required to proceed to INSPECTION.

The inspector can attest only after that version-bound review and can reference only evidence examined in that cycle. The attestation retains INSPECTION while advancing the application version; it does not introduce a post-inspection EVIDENCE_REVIEW state. The reviewer can recommend only after the actual attestation. Screening, evidence assessment, inspector findings, recommendation and the independent Directorate decision remain separate facts. Neither screening nor evidence sufficiency is an affiliation decision or an inspector's MET finding.

Exact consecutive immutable revision links bind the assignment, screening, pre-inspection evidence review and attestation. Current positive recommendations/decisions follow those links, recheck assessed evidence and existing required findings, and retain current case/criterion/scanner/independence guards. Timestamps do not select an older cycle. All recommendations require an attributed screened attestation, including a new rejection recommendation. A central rejection of an already recommended historical case remains an adverse-history operation; it grants no positive recognition.

The assigned reviewer may request criterion-scoped correction during SCREENING, EVIDENCE_REVIEW, INSPECTION or RECOMMENDED. Resubmission clears current assignments/recommendation and returns to SUBMITTED for a fresh complete cycle. Pending screening can also be intentionally withdrawn. Previous requests/responses/assignments/evidence/inspections/decisions remain retained; withdrawal changes no prior facility affiliation. Current scope still governs cached receipt access. Current-stage metadata is returned independently of the displayed historical page.

Legacy pending dossiers without this actual screening/review chain fail closed for inspection or positive recognition. A reviewer can request correction and the scoped applicant can resubmit for a fresh cycle; no historical screening is invented and no immutable revision is rewritten. Production contained no dossiers at the prior release; actual counts must be rechecked before deployment. No conversion or schema marker deletion is needed. A legacy-shaped engineering fixture is explicitly labelled and does not claim that those historical transitions were executed by the old runtime.

This closes the implemented initial-order gap, not complete canonical semantic parity or operating acceptance. The [criterion correction extension](application-workflow-extension.md) remains narrower than the full corrective-action contract. No institutional deadline, operating approval, officer or scanner result is supplied by this extension.

Uploads remain excluded without the existing actual scanner/private-storage prerequisites. Metadata-only synthetic CLEAN fixtures qualify no malware service or file. No extra host, provider, dependency, fee or AI approval is introduced.
