# Bounded cloud capacity qualification

Ticket LWH-AUD-20261109-002 remains open until representative capacity, simultaneous corrections/replay and adopted targets are qualified. This harness measures the existing reporting implementation inside a disposable Vercel preview backed by an isolated schema in the existing Neon database. It adds no project, persistent worker/scanner host, dependency or operating approval.

From a clean, committed checkout with successful exact-commit CI, use the existing D-drive environment and run `python scripts/verify_capacity_cloud.py`. Production aliases and project environment settings are never changed. The preview uses `scripts/capacity_candidate.py` in place of the production entrypoint, explicit environment overrides, a separate one-use encryption key and only the disposable schema. The ordinary production `NullPool` and reporting business code are retained. The local fixture installer may use a pool to avoid Windows TLS overhead; setup timings are excluded from cloud measurements.

The wrapper rejects production deployment and non-disposable schema names, excludes every route except readiness/reporting, blanks outbound provider settings, and removes cron scheduling. Reporting actors and decisions are labelled synthetic and confined to the disposable schema. Preview source hashes are verified. Protected probes use the existing temporary header authentication and revoke it afterward. The preview is deleted, its absence checked and the disposable schema removed. Preserve failed measurements and cleanup results. Do not promote this wrapper: its entrypoint/config/source identity differs from production and it has no production release metadata.

Measure baseline extraction, 5,001 unrelated later-period records, duplicate receipts, simultaneous facilities, repeated 5,000-record extraction, 20,000 selected signed events, each overflow boundary and retained extraction history. Missing summaries must remain UNKNOWN with complete accounting. Overflow must return SOURCE_BATCH_REQUIRED without truncated totals. The ordinary fixture's correction/stale-source checks run before cloud measurements. A short repeated sequence is not a sustained correction/replay/load qualification.

Response instrumentation records elapsed application milliseconds, client wall time and Linux process-lifetime high-water RSS in KiB. RSS is **not per-request allocation, remaining memory, provider billing memory or an isolated concurrency sample**. Client time includes network/cold start. Application time excludes upstream cold start and is not provider-billed duration. Keep the deployed 60-second maximum; never raise caps to make a benchmark pass. Record timeout/failure honestly and use it to choose bounded or incremental follow-up work. No latency target is adopted by this harness.
